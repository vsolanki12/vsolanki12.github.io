Summary: Ingress operator enters Degraded=True during HyperShift guest cluster router replacement
Test date: 2026-09-10 UTC
Validation status: RACE REPRODUCED Fix status: NOT IMPLEMENTED

Executive Summary

  • The transient ingress status race was reproduced on an AWS HyperShift guest cluster.
  • The router replacement became Ready before the Deployment became Available.
  • The Deployment uses minReadySeconds: 30, and the ingress Degraded calculation currently grants the same 30-second grace period.
  • Result: Degraded=True appeared briefly and cleared after the replacement became Available.
  • Recommended fix: increase the DeploymentAvailable Degraded grace to 60 seconds, with focused regression tests and protection against hiding a sustained outage.
  • No HyperShift-specific MonitorTest exception or broad test skip is recommended.

Root Cause Analysis

READINESS / AVAILABILITY TIMING RACE
ComponentCurrent behaviorEffect
HyperShift infrastructure policy SingleReplica maps to SingleReplicaTopologyMode. Only one guest router is deployed.
Router Deployment minReadySeconds: 30. A Ready pod is not immediately counted as Available.
Ingress Degraded status DeploymentAvailable=False has a 30-second grace period. The grace expires at the same time as Deployment stabilization.

The replacement router was healthy before the Deployment became Available, but the ingress operator evaluated the 30-second grace before the Deployment controller completed its availability calculation.

Suggested Fix

PROPOSED PRODUCT FIX — cluster-ingress-operator

Change the DeploymentAvailable grace used by computeIngressDegradedCondition from 30 seconds to 60 seconds.

Proposed change 
expectedConditions := []expectedCondition{
    {
        condition: IngressControllerDeploymentAvailableConditionType,
        status:    operatorv1.ConditionTrue,
-       gracePeriod: time.Second * 30,
+       gracePeriod: time.Second * 60,
    },
}

This gives the replacement router time to pass readiness checks and the existing 30-second minReadySeconds interval before the operator reports Degraded.

Required safety check: the implementation must not hide a sustained single-router outage indefinitely. If a blanket 60-second grace is considered too broad, make the grace conditional on an active replacement that is Ready while Deployment availability is still stabilizing.

Limitations and Scope

Important: the standard serial e2e taint is already tolerated by the router: kubernetes.io/e2e-evict-taint-key=evictTaintVal:NoExecute. The controlled test used a custom taint to reproduce the timing race. Therefore, this report verifies the status race but does not prove that the exact historical CI eviction used the standard e2e taint.
  • Do not add a broad MonitorTest exception.
  • Do not reduce minReadySeconds without ingress owner approval.
  • Do not add broad NoExecute tolerations; they could keep routers on unhealthy nodes.
  • The separate Available-condition work in OCPBUGS-92835 does not fully address this Degraded transition.

Final Verdict

  • Status: RACE REPRODUCED
  • Root cause: replacement readiness completed before Deployment availability stabilization.
  • Recommended owner: openshift/cluster-ingress-operator.
  • Recommended first patch: 60-second DeploymentAvailable Degraded grace plus focused unit/e2e regression coverage.
  • MonitorTest exception: not recommended.
