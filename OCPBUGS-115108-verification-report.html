Executive Summary

  • The transient ingress status race was reproduced on an AWS HyperShift guest cluster: the replacement router became Ready before the Deployment became Available.
  • During initial external-control-plane startup, the ingress operator can run before any eligible guest node exists. The router cannot schedule in that expected state, so startup-dependent conditions must not immediately make ingress Degraded.
  • The operator now records the initial AwaitingNodes state, continues evaluating load-balancer and DNS failures, and resumes normal router evaluation when the first eligible Ready node appears.
  • When node waiting ends, deployment, replica, and canary transition times are reset so the grace period starts at node availability.
  • The deployment grace is derived as MinReadySeconds + 30 seconds; for minReadySeconds: 30, the effective grace is 60 seconds.
  • Live result: with the patched operator, the replacement became Available and Degraded=False remained stable throughout the live eviction test.
  • Live startup result: on a fresh HCP with zero guest nodes, the patched operator reported Available=False, Reason=AwaitingNodes and Degraded=False instead of treating the unschedulable router as an outage.
  • Focused transition result: the aged AwaitingNodes to Ready-node transition was validated with deterministic unit coverage; the worker bootstrap itself did not complete on the disposable live HCP.
  • PR: OCPBUGS-115108 is open against openshift/cluster-ingress-operator.
  • No HyperShift-specific MonitorTest exception or broad test skip is recommended.

Root Cause Analysis

HCP STARTUP AND READINESS / AVAILABILITY TIMING WINDOWS
ComponentCurrent behaviorEffect
External-control-plane startup The ingress operator can start before any guest worker node is Ready. The router Deployment has no eligible node and cannot create an available replica yet.
HyperShift infrastructure policy SingleReplica maps to SingleReplicaTopologyMode. Only one guest router is deployed.
Router Deployment minReadySeconds: 30. A Ready pod is not immediately counted as Available.
Ingress Degraded status DeploymentAvailable=False has a 30-second grace period. The grace expires at the same time as Deployment stabilization.
Status transition timestamps Conditions ignored while waiting for a guest node can retain an old transition time. When the first eligible node appears, degradation could be evaluated immediately using stale elapsed time.

There are two related timing windows. During initial HCP startup, the old logic treated the expected absence of a schedulable guest node as an ingress failure after the grace expired. After node waiting ended, stale condition timestamps could make the operator evaluate the deployment grace as already expired. The fix handles the initial state explicitly and starts fresh grace periods when node availability begins.

The ClusterOperator condition contract is preserved: this is not a broad suppression of Degraded. Load-balancer and DNS failures remain evaluated, and a cluster that had initialized and then loses its eligible nodes still reports a real outage.

Implemented Solution

IMPLEMENTED PRODUCT FIX — cluster-ingress-operator

The implementation has two complementary safeguards. It avoids classifying the initial absence of an eligible guest node as an ingress outage, and it derives the DeploymentAvailable grace used by computeIngressDegradedCondition from the router Deployment's minReadySeconds, plus a 30-second recovery buffer.

Initial HCP node handling

  • For external control-plane topology, the operator checks the router Deployment's node selector, required affinity, taints, unschedulable flag, and NodeReady condition.
  • Before the first eligible Ready node exists, the ingress status records AwaitingNodes and excludes only startup-dependent deployment, replica, and canary conditions from Degraded evaluation.
  • Load-balancer and DNS conditions continue to participate in Degraded evaluation.
  • Once the first eligible node appears, the operator resumes normal evaluation and resets the startup-dependent condition transition timestamps.
Node-wait transition 
if wasWaitingForNodes && !waitingForNodes {
    resetIngressStartupConditionTransitionTimes(updated.Status.Conditions)
}
Implemented change 
expectedConditions := []expectedCondition{
    {
        condition: IngressControllerDeploymentAvailableConditionType,
        status:    operatorv1.ConditionTrue,
+       gracePeriod: time.Duration(minReadySeconds)*time.Second + 30*time.Second,
    },
}

The implementation uses deployment.Spec.MinReadySeconds at reconciliation time. When the value is zero, the existing 30-second behavior is preserved; when it is 30, the effective grace is 60 seconds.

Safety property: this is not an indefinite suppression. A sustained outage becomes Degraded after the configured minReadySeconds plus the fixed 30-second buffer.

Limitations and Scope

Important: the standard serial e2e taint is already tolerated by the router: kubernetes.io/e2e-evict-taint-key=evictTaintVal:NoExecute. The controlled test used a custom taint to reproduce the router replacement timing race. Therefore, this report verifies the replacement status race but does not prove that the exact historical CI eviction used the standard e2e taint.
  • The disposable HCP worker EC2 instance launched and Ignition completed, but the guest kubelet did not register a Node during the test window. Therefore the first-worker transition is supported by deterministic unit coverage, while the no-node startup result is live evidence.
  • The disposable HCP used an intentionally incomplete load-balancer setup; after its independent load-balancer grace expired, Degraded=True was correctly reported for LoadBalancerReady=False.
  • Do not add a broad MonitorTest exception.
  • Do not reduce minReadySeconds without ingress owner approval.
  • Do not add broad NoExecute tolerations; they could keep routers on unhealthy nodes.
  • The separate Available-condition work in OCPBUGS-92835 does not fully address this Degraded transition.
  • For normal upgrades and post-initialization node loss, genuine Degraded conditions remain reportable.
